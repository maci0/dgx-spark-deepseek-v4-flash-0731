## 2. KV cache sizing

Measured: **12.27 GiB of fp8 KV = 1,448,712 tokens** (~8.9 KB/token over 43 layers).

Projection for NVFP4 KV in the same 12.27 GiB:

| KV dtype | bytes/element | tokens | max 1M-token contexts |
|---|---|---|---|
| `fp8` (current) | 1.0 | 1,448,712 | 1.38× |
| `nvfp4_ds_mla` + block scales | ~0.5625 | ~2.58 M | ~2.4× |
| nvfp4 ideal | 0.5 | ~2.90 M | ~2.8× |

**`nvfp4_ds_mla` is supported by the running image** (verified in
`vllm/config/cache.py`). Untested here, switching `kv_cache_dtype` is a
one-line recipe change and is the single biggest lever on total KV capacity.
Caveat: accuracy impact unmeasured, and DS-MLA nvfp4 was previously noted as
0.21-only, which is the version in use.

## 3. Bugs found and fixed (root-caused, not worked around)

### 3.1 systemd `RemoveIPC` destroying worker semaphores, **highest impact**
`logind.conf` defaults to `RemoveIPC=yes` with `Linger=no`. The worker node is
started over SSH; when that login session closed, systemd deleted all POSIX
semaphores owned by the user, including vLLM's `MultiprocExecutor` ones:

```
File ".../multiprocessing/synchronize.py", line 115, in __setstate__
    self._semlock = _multiprocessing.SemLock._rebuild(*state)
FileNotFoundError: [Errno 13] No such file or directory
```

The head does **not** error, it blocks forever on the next collective. This
masqueraded as `shm_broadcast` stalls, GPU pinned at 96 % with no progress,
frozen cudagraph capture, and `DistStoreError: 1/2 clients joined`.

**Tell:** the worker container is up but has **no `Worker_TP` process at all**.
"Worker idle" actually meant "worker dead".

**Fix (persists across reboots, no root needed):**
```bash
loginctl enable-linger maci      # on BOTH nodes
loginctl show-user maci | grep Linger   # must be Linger=yes
```

This had corrupted a large share of earlier conclusions, several "b12x kernel
deadlocks" were really this.

### 3.2 b12x CUTLASS GEMM hangs on non-default CUDA streams
`py-spy` (needs `CAP_SYS_PTRACE`, see §5) showed the worker blocked in:

```
run_compiled_program (cutlass/base_dsl/jit_executor.py)
dense_gemm_fused_quant_a (b12x/_lib/dense_gemm.py)
_block_fp8_linear_mxfp8_fused_op (b12x/gemm/_shared/block_fp8.py)
...
execute_in_parallel (vllm/utils/multi_stream_utils.py:212)
_run_parallel_input_projections (vllm/models/deepseek_v4/attention.py:717)
```

`execute_in_parallel` dispatches attention input projections onto auxiliary CUDA
streams; the b12x CUTLASS DSL GEMM does not tolerate that here. The function
already has a serial fallback when its `enable` argument is falsey, so forcing
that path fixes it. Applied via `sitecustomize.py` on a writable mount +
`PYTHONPATH`, patching at import time (must be before `attention.py` binds the
symbol).

### 3.3 Headless worker parent exits prematurely
`vllm/entrypoints/cli/serve.py: run_headless()` does:
```python
executor.start_worker_monitor(inline=True)
return        # process exits the moment the monitor returns
```
The monitor blocks on `multiprocessing.connection.wait(sentinels)`, which
returned spuriously **while the worker was still initialising**: the parent
then SIGKILLed a healthy worker (its log showed the worker completing DSpark
speculator capture *after* shutdown began). Patched to a real liveness poll.

### 3.4 Root-owned HuggingFace cache dirs on spark2
`~/.cache/huggingface/hub` and `hub/.locks` were `root:root` from earlier
docker-compose-as-root runs, so downloads failed with `PermissionError`.

**Fix without sudo:** the parent `hub/` is user-owned, so the root-owned
`.locks` can be renamed aside and recreated:
```bash
mv ~/.cache/huggingface/hub/.locks ~/.cache/huggingface/hub/.locks.root
mkdir ~/.cache/huggingface/hub/.locks
```

### 3.5 sparkrun distributes models itself
sparkrun fetches into the standard `hub/` cache and ignores `HF_HUB_CACHE`
overrides, so a model staged elsewhere is invisible and it re-downloads 156 GB
per launch. Keep checkpoints in `~/.cache/huggingface/hub/`.

## 4. Measurement pitfalls (these produced false conclusions)

1. **Cold vs warm cache, up to 2.5× swing.** Two consecutive runs of the *same*
   config measured `c1 = 23.7` then `59.4` tok/s. Always warm up, then take
   ≥2 measurements and compare like with like.
2. **Run-to-run variance ~4 %.** The same config gridded 56.95 (Aug 18) and
   54.60 (Aug 20). Differences under ~5 % are noise.
3. **`ignore_eos` matters.** Without it, early EOS shortens requests and inflates
   per-request overhead, depressing tok/s.
4. **Prefix caching skews grid rows.** With `--enable-prefix-caching`, the first
   cell of a row pays a cold prefill and later cells reuse the prefix, making
   c1-at-depth look catastrophically slow versus c2/c5/c10.
5. **Wrong port.** eugr/SGLang recipes serve on **8000**; the stage-c record
   recipe serves on **8888**. Health-checking the wrong port produced a string of
   phantom "never healthy" failures.
6. **`Starting vLLM server` is absent** from the sparkrun launcher log (it goes to
   the container's own log), so its absence is not evidence of failure.
7. **Idle ≠ deadlocked.** `EngineCore` in `run_busy_loop`→`queue.get()` and
   `Worker_TP` in `shm_broadcast.dequeue` is the normal *ready and waiting* state.
8. **`pkill -f <pattern>` matches your own SSH command line** and silently kills
   the shell mid-script. Use `pkill -f "[p]attern"`.

## 5. Diagnostics

`py-spy` needs `CAP_SYS_PTRACE`; the host also has `kernel.yama.ptrace_scope=1`,
which restricts ptrace to direct children (hence host-side py-spy fails).
sparkrun's rootless mode hardcodes `cap_add = []` and a recipe-level `cap_add:`
does **not** override it. Patch the installed sparkrun:

```
.../sparkrun/orchestration/executors/docker.py
  adjustments["cap_add"] = []   ->   ["SYS_PTRACE"]
```
(applies to every copy under `~/.cache/uv/archive-v0/*/`). Then
`docker exec -u 0 <cid> py-spy dump --pid <pid>` works.

## 6. Tuning results (all measured)

Baseline = the production config above.

| Change | Result |
|---|---|
| `num_speculative_tokens` 3 → 5 | **−6.7 %** (49.99 vs 53.57, 28-cell). Collapses at c1/deep context. Recipe's "k=5 is ~24 % faster" note applies to short-context single-stream only. |
| `VLLM_USE_B12X_MHC=1` | +1.9 % locally (inside noise); **officially worse**: arena raw decode 37.95 vs 44.75 baseline |
| `VLLM_USE_B12X_SPARSE_INDEXER=1` | −2.6 %; harms deep context (Lightning Indexer does most work at long context) |
| `VLLM_USE_B12X_FP8_GEMM=1` | **crashes**: `DeepGEMM/utils/layout.hpp:39: t.dim() == N` |
| `long_prefill_token_threshold` 1024 → 4096 | neutral |
| `--load-format fastsafetensors` | ~3× faster load (60 s vs 3m17s) but **OOM-kills the worker** on unified memory |

**Conclusion:** the production recipe is well tuned; every knob tried is neutral,
worse, or crashes. Remaining untested levers: `kv_cache_dtype: nvfp4_ds_mla`
(§2), `max_num_seqs` (12 → 16/24), `gpu_memory_utilization` (0.78 → 0.85, which
is what upstream now ships).

## 7. b12x availability (important)

| Component | arm64 / DGX Spark? |
|---|---|
| b12x kernels (v1.2.3) | ✅ inside `eugr/spark-vllm-b12x` |
| vLLM + b12x | ✅ current, in use |
| SGLang, arm64 | ✅ `scitrera/dgx-spark-sglang:0.5.17`: **no b12x** |
| SGLang + b12x | ❌ community images (`voipmonitor/sglang`, `lukealonso/sglang-cuda13-b12x`) are **amd64 only** → `exec format error` |
| b12x upstreamed to SGLang | ❌ not upstream |

A port was scoped and rejected: the b12x fork of SGLang is ~0.5.12-era (May) and
written against b12x **0.8/0.10**, while the arm64 package is **1.2.3**, whose
`integration/` layer was refactored to be vLLM-only (`attention.py`, `mla.py`,
`nsa_indexer.py`, `tp_moe.py` all removed). Five of ten required symbols no
longer exist. A working port means writing a new SGLang↔b12x bridge against
undocumented internals, days of work, unproven payoff.
